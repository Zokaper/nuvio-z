## The two clusters

These nine files are the structural problem, and naming them is the point of this document.

| Cluster | Files | Our commits | What is wrong with it |
| --- | --- | --- | --- |
| `PlayerScreenRuntime*` | `SourceActions`, `Ui`, `Effects`, `State`, plus the screen | **53** | Nuvio Z threads playback-mode state through upstream's player runtime by editing it inline rather than by an extension point. |
| `PlayerSettings*` | `Storage.kt` + android/ios/desktop actuals, `Repository` | **49** | Every new synced key needs an edit in four places, all of them upstream-owned. |

**Rule 6 applies: refactor a file into a seam the first time a sync conflicts in it**, not before.
Rewriting all nine in advance is speculative work against a merge that has not happened yet.

The right shape, when the time comes, is the one the playback package already has: Z logic lives in
`features/playback/**` (100% ours, zero conflict risk) and the upstream file holds one call.

## Reviewing this file

At every sync, for each row:

1. Is the reason still true, or has the Z code moved somewhere better?
2. Did upstream touch this file since the last sync? If so it is a real conflict, not a theoretical
   one.
3. Did the merge conflict here? If yes, **that is the trigger for rule 6** - refactor it into a seam
   now, in the same pass.

A row with no reason is a refactor waiting to happen. A row that has not conflicted in three syncs
is fine where it is.
